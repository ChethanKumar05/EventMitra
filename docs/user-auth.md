# User signup and phone OTP authentication

User bank account add/list/get and default-only updates are documented in [People and account APIs](people-and-accounts-api.md). Apply migration 014 before using `/api/user/accounts`.

Run `npm run migrate` before using these endpoints. Migration **013** generates `USR00001` style user codes, adds phone verification and independent user sessions, and changes `user_phone_verification` to use `country_code` + `user_phone_number` with **no `user_id`**. Earlier migration files are unchanged. Historical OTP records retain their phone targets but are expired and consumed.

Base URL: `http://localhost:3600/api/user/auth`. Send `Content-Type: application/json` for JSON bodies.

The flow is **signup → login → verify OTP → authenticated requests → logout**. Signup creates an active, pending user without a session or an OTP. Call login next to get the challenge. Existing users start at login. Resend returns a new challenge and invalidates the previous token. Phone verification sets `is_phone_number_verified=true`; it does not change administrative approval status. Active users with status `pending` or `verified` can log in. Other statuses and inactive accounts cannot authenticate.

**Development OTP is `1111`. No SMS is sent.** Login, resend and verification return `503` in production until a real delivery provider is implemented. Signup itself does not require SMS configuration.

| Method | Path | Body | Success |
| --- | --- | --- | --- |
| POST | `/signup` | Signup fields below | 201, pending user |
| POST | `/login` | `country_code`, `user_phone_number` | 200, OTP challenge; no session |
| POST | `/resend-otp` | `country_code`, `user_phone_number` | 200, replacement OTP challenge |
| POST | `/verify-otp` | `otp`, `otp_token` | 200, user and session cookie |
| GET | `/me` | None; user cookie required | 200, current user |
| POST | `/logout` | None | 200, revokes current session and clears cookie |

## Signup

```json
{
  "country_code": "+91",
  "user_phone_number": "9876543210",
  "user_name": "Ravi Kumar",
  "gender": "m",
  "email": "ravi@example.com",
  "profile_image": "/uploads/user-profile.jpg",
  "whatsapp_number": "+919876543210",
  "alternative_number": "9876543211"
}
```

| Field | Required | Validation |
| --- | --- | --- |
| `country_code` | Yes | String such as `+91`; `+` followed by 1–3 digits, first nonzero |
| `user_phone_number` | Yes | National number string, 7–15 digits, first nonzero; combined country code and number at most 15 digits |
| `user_name` | Yes | Nonempty string, maximum 150 characters; surrounding/repeated whitespace normalized; control characters rejected |
| `gender` | Yes | `m` or `f`, matching the existing schema |
| `email` | No | Valid email format, normalized to lowercase; unique when provided |
| `profile_image` | No | Nonempty image reference, maximum 2048 characters; this endpoint does not upload files |
| `whatsapp_number` | No | String of 7–15 digits, optional leading `+` |
| `alternative_number` | No | String of 7–15 digits, optional leading `+` |

Optional fields may be omitted, `null` or `""`; they are stored as `null`. Names need not be unique. Country code and user phone number together must be unique. Duplicate phone/email returns `409`. `user_id`, `user_code`, `status`, `is_active`, verification flags, passwords and all other unsupported fields are rejected with `400`. Codes and IDs are generated by the server. Login has no email/password option.

## Login and resend

Use this body for both `POST /login` and `POST /resend-otp`:

```json
{
  "country_code": "+91",
  "user_phone_number": "9876543210"
}
```

Example response (`otp_token` is different for each request):

```json
{
  "status": true,
  "message": "If the account is eligible, a test OTP challenge is available",
  "code": 200,
  "data": {
    "otp_token": "<64-character random hex token>",
    "expires_in": 300,
    "delivery": "development-fixed-otp"
  }
}
```

Unknown and inactive/disallowed accounts receive the same challenge response; verification cannot create a session for those accounts. Sign up first and request a fresh login OTP afterward. A challenge issued before signup, or for an account later deleted/recreated with the same phone, cannot authenticate the new account. Resend accepts the phone fields only; it does not require an old token or an existing session.

## Verify OTP

Use the **latest** token returned by login or resend:

```json
{
  "otp": "1111",
  "otp_token": "<paste the latest otp_token here>"
}
```

Both fields must be strings. Tokens must be 64 lowercase hexadecimal characters. Successful verification consumes the challenge atomically, marks the phone verified and returns the user record in `data`. It also sets an eight-hour HttpOnly, SameSite=Strict cookie: `eventmitra_user_session` (production configuration uses Secure `__Host-eventmitra-user`). Keep the Postman cookie jar enabled. Browser clients must send cookies with authenticated requests; origin checks follow the existing same-origin owner/admin policy.

`GET /me` and `POST /logout` have **no body**. Logout is idempotent and revokes only the presented user session. Admin and owner sessions are separate. Disabling the user, applying an ineligible status, changing the phone/country code, clearing phone verification or deleting the account revokes sessions. Re-enabling the account does not restore old sessions. Phone/status/inactive changes also invalidate outstanding OTPs.

## Limits and errors

- OTP lifetime: 5 minutes; each token is single use.
- Five wrong OTP attempts exhaust the challenge. Wrong attempts persist; the fifth returns `429`.
- Login and resend share a limit of 5 challenges per phone and 20 per IP in 15 minutes.
- Signup: 20 requests per IP in 15 minutes. Verification: 100 requests per IP in 15 minutes.
- `400`: malformed body, unknown fields or invalid formats. `401`: invalid/expired/used challenge or missing session. `403`: cross-site request. `409`: duplicate signup identity. `429`: rate/attempt limit. `503`: test OTP endpoints called in production.
- Raw OTP/token/session values are not stored. OTP hashes are bound to the random challenge token; the database stores the token digest. A one-way account fingerprint prevents a phone challenge from authenticating a replacement account without storing `user_id` on OTP records.

## Postman and integration tests

Import [User collection](postman/EventMitra.User.postman_collection.json) and [User local environment](postman/EventMitra.User.local.postman_environment.json). Select **EventMitra - User Local**. Fill `user_name`, `user_phone_number` and `country_code`; optional `user_email` may remain empty. All JSON fields are visible in request bodies. No accounts or default credentials are supplied.

Run signup once per account. Then run Login, Resend OTP, and Logout folders in order. Login/resend scripts save tokens automatically; verification establishes the cookie. The resend folder demonstrates that the superseded token fails before verifying the latest one. For an existing account, skip signup. Do not mix these requests with the owner collection.

```bash
npm run typecheck
npm run build
npm test
npm run test:user:integration:local
```

The local integration command creates a temporary isolated database using the configured PostgreSQL connection and drops it afterward; it does not migrate the application database. The connection needs CREATE DATABASE permission. Alternatively, set `USER_TEST_DATABASE_URL` to a fresh expendable database ending in `_test` and run `npm run test:user:integration`. `npm run test:integration:local` runs admin/security, owner and user suites in separate temporary databases.
