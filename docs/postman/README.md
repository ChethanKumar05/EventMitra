# EventMitra Postman setup

Reimport the Owner/Admin/User/Booking collections and environments for migrations 018/019. Owner signup needs `owner_user_name`; admin owner creation needs `managed_owner_user_name`. Owner login accepts `user_name` or email. Set `venue_address` for venue create/update examples. Owner venue list items now include `venue_meals_details`, `venue_price_details` and `venue_decoration_details`. Owner, Admin and User collections each have a shared multipart upload folder; select a local file and run it separately after login. See [upload setup](../uploads-api.md).

Booking and notifications have a separate [Booking collection](EventMitra.Booking.postman_collection.json) and [Booking environment](EventMitra.Booking.local.postman_environment.json). Apply migrations 016/017, start the API and `npm run booking:worker`, and fill existing user/owner/admin credentials plus venue, valid price and future date. Run folders individually with the cookie jar enabled. Owners accept before the user pays the configured advance. Checkout runs in the frontend; paste its real payment callback ID/signature to verify. FCM samples skip without actual tokens; refund samples skip unless `run_refund_examples=true`. Provider secrets remain on the server. See [Booking routes, bodies and provider setup](../booking-api.md).

Owner/Admin venue folders now include three GET price dropdowns before price creation: `/:venueId/type-slots/dropdown`, `/:venueId/decorations/dropdown`, `/:venueId/meals/dropdown`. They return `data` arrays with `value`, `label` and relevant pricing fields. No body is needed; venue ID is in the URL. See [Price dropdown documentation](../venue-management-api.md#price-dropdowns).

Venue slot/decoration/meal/price save requests use one POST endpoint per resource. Create bodies set the record ID to null (omission also works); update bodies send the existing `venue_type_slot_id`, `venue_decoration_id`, `venue_meals_id` or `venue_price_id`. The venue ID remains in the URL. The separate child PUT routes are removed. Reimport Owner/Admin collections for these bodies. Creation returns 201 and updates 200; GET venue detail returns existing row IDs. See [Frontend record selection](../venue-management-api.md#frontend-record-selection).

Migration 015 adds owner/admin venue management. Reimport the Owner and Admin collections/environments. Their new venue folders log in first, capture venue/slot/package IDs, and demonstrate full-detail APIs. Set `venue_name`; admins also set `venue_owner_id` from the paginated owner dropdown. Ordinary admins need `venue_management` action grants. Owner edits to Active venues return them to Pending. See [Venue API payloads](../venue-management-api.md). Run the venue folder separately against existing credentials; admin sample cleanup is optional.

Migration 014 adds admin user/owner management and bank accounts. Reimport all three collections and environments. The admin collection has new managed-profile/account folders. The user and owner collections have separate bank-account folders that log in first. Fill the new bank fields in the corresponding environment. Self-service PUT sends only `is_default`; admin PUT can edit bank details. See [People/account payloads and permissions](../people-and-accounts-api.md). Repeated adds count toward the five-account limit; profile deletion samples preserve history.

1. Import `EventMitra.postman_collection.json` and `EventMitra.local.postman_environment.json`.
2. Select EventMitra - Local. Set base_url if needed (default http://localhost:3600, no trailing slash).
3. Set admin_email/admin_password to your own super admin and new_admin_password to a private
   password for the sample admin (minimum 12 characters). Supplied credential values are empty.
4. Run `npm run migrate`, then `npm run admin:bootstrap` if the first super admin does not exist.
   Start the server with `npm run dev`.
5. Run folders in order: Health, Authentication, Roles, Admins, Main modules, Per-admin module
   permissions, Cleanup/logout. Public venues are independent. Login uses the cookie jar; keep it enabled.

Bodies show JSON fields directly. Replace field values yourself or use the environment variables.
The collection resolves strings safely, including passwords containing quotes and backslashes.
Create responses capture role_id, admin_id, module_id and permission_id. Codes are generated by
the API: ADM, RL, MOD and PER prefixes. Login and auth/me return effective module action flags.

The flow assigns flags to the selected admin and current role in admin_permission; there are no
submodules. The matrix save atomically replaces that admin's grant set, preserving IDs of existing
rows. Cleanup removes only the sample assignment, module, admin and role, then logs out.
Use a development database for a full run. To inspect records, stop before the cleanup folder.

List requests include page/limit and disabled optional search_column, search, sort_by, sort_order
and field filters in Params. Enable the ones you need. Changing an admin's role clears grants
and revokes sessions; reassign permissions for the new role. Security writes require super admins.

Reimport the collection to replace the previous role-permission catalog flow. Legacy catalog
endpoints remain on the server for compatibility but are not used for runtime authorization.

Updated login accepts admin_login (email or username); admin_email remains a fallback. New admin bodies include required admin_username. Permission create/update is now one POST /admin-permissions with a visible array body and HTTP 200 response. It preserves existing IDs and omitted flags. No separate per-record PUT request remains. Reimport the collection and environment for these changes.

Owner authentication has its own collection and environment, independent of the admin flow:
[Owner collection](EventMitra.Owner.postman_collection.json),
[Owner environment](EventMitra.Owner.local.postman_environment.json).
See [owner login/logout setup and test instructions](../owner-auth.md). Run only the folder
for your chosen login method; owner_name is a display name and is no longer accepted for login. Use owner_user_name or email.

The Owner collection now includes Signup, email/phone Send OTP + Verify OTP, and email/phone Forgot Password + Reset Password folders. Test OTP is 1111; no email/SMS delivery is connected. See [Owner signup/OTP](../owner-signup-otp.md). Signup first, then verify. Migration 018 requires a unique owner_user_name; display names can repeat. Normal verification captures owner_access_token; password-reset proof does not log in.

User signup and phone OTP login have a separate [User collection](EventMitra.User.postman_collection.json) and [User environment](EventMitra.User.local.postman_environment.json). Apply migration 013, select **EventMitra - User Local**, and fill `user_name`, `country_code`, `user_phone_number` (optional `user_email`). Run signup once, then Login, Resend OTP and Logout folders. Tokens are saved automatically; keep the cookie jar enabled. Both login and resend accept `country_code` + `user_phone_number`; verify accepts `otp` + `otp_token`. The test OTP is `1111`, and these OTP endpoints are disabled in production. See [User flow and copyable bodies](../user-auth.md).
